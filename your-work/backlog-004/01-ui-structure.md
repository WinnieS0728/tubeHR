# UI 結構描述

## 1. 入口與路由

### 1.1 建議路由

```
/admin/offboarding                    → 離職交接總覽（HR / 主管）
/admin/offboarding/[checklistId]      → 單一員工交接詳情（主操作頁）
```

掛在現有 `(admin)` layout 下，與 `/admin/forms` 並列。側邊導覽新增「離職交接」項目，僅 `HR Admin` 與 `Direct Manager` 可見（權限由後端回傳 `capabilities` 決定，前端不 hardcode role name）。

### 1.2 進入方式

| 觸發 | 入口 |
|------|------|
| HR 建立離職流程 | 總覽頁「新增離職交接」→ 選員工 → 跳詳情頁 |
| 員工在 CustomerWeb 提離職（系統自動） | 總覽頁出現新列，主管收到通知 deep link |
| 主管從通知進入 | 直接開 `/admin/offboarding/[checklistId]` |

## 2. 總覽頁（`/admin/offboarding`）

### 2.1 頁面結構

```
┌─────────────────────────────────────────────────────────┐
│ PageHeader: 離職交接清單                                  │
│ [篩選: 狀態 ▼] [篩選: 部門 ▼] [搜尋員工]  [+ 新增離職交接] │
├─────────────────────────────────────────────────────────┤
│ SummaryCards (4 格)                                      │
│  進行中 N │ 卡住 N │ 今日截止 N │ 已凍結 N                  │
├─────────────────────────────────────────────────────────┤
│ DataTable / CardList                                     │
│  員工 │ 最後在職日 │ 截止時間 │ 進度(4/4) │ 狀態 │ 操作    │
│  ...                                                     │
└─────────────────────────────────────────────────────────┘
```

### 2.2 資訊密度

- **Desktop**：表格列，每列顯示四區塊進度 mini-bar（●●○○ = 2/4 完成）。
- **Tablet 以下**：改 card list，每張 card 顯示員工頭像、姓名、倒數、狀態 badge。
- 預設排序：`deadlineAt ASC`（越急越上），次排序 `status`（凍結 / 卡住優先標紅）。

### 2.3 空狀態

| 情境 | 文案 | CTA |
|------|------|-----|
| 無任何離職交接 | 「目前沒有進行中的離職交接」 | 「新增離職交接」（HR）/ 無 CTA（純主管） |
| 篩選無結果 | 「沒有符合條件的交接項目」 | 「清除篩選」 |

## 3. 詳情頁（`/admin/offboarding/[checklistId]`）— 核心頁

### 3.1 整體布局（由上而下）

```
┌─────────────────────────────────────────────────────────┐
│ A. Sticky Header — 員工摘要 + 全局狀態                      │
├─────────────────────────────────────────────────────────┤
│ B. Deadline Banner — 倒數 / 凍結警告（條件顯示）             │
├─────────────────────────────────────────────────────────┤
│ C. Progress Stepper — 四區塊完成度（可點跳 anchor）          │
├─────────────────────────────────────────────────────────┤
│ D1. 區塊一：下屬重新指派                                    │
│ D2. 區塊二：表單模板負責人重新指派                             │
│ D3. 區塊三：待簽核單跨權代理                                  │
│ D4. 區塊四：內部系統權限清單                                  │
├─────────────────────────────────────────────────────────┤
│ E. Footer Actions — 標記完成 / 申請延期（HR）/ 匯出報告      │
└─────────────────────────────────────────────────────────┘
```

### 3.2 A. Sticky Header

| 元素 | 說明 |
|------|------|
| 員工頭像 + 姓名 + 工號 | 來自 HR master data |
| 部門 / 職稱 | |
| 最後在職日 (D) | 可編輯（僅 HR，需二次確認 modal） |
| 全局狀態 Badge | `進行中` / `卡住` / `已完成` / `已凍結` |
| 整體進度 | `3/4 區塊完成` + 環形或線性 progress |

**凍結態**：Header 加灰色 overlay 感，所有 mutation 按鈕 disabled，保留「匯出」與「聯絡 HR」。

### 3.3 B. Deadline Banner

| 條件 | 樣式 | 文案範例 |
|------|------|----------|
| D-3 以前 | 無 banner 或 info 蓝 | — |
| D-3 ~ D-1 | warning 黄 | 「距離截止還有 2 天 4 小時（D 日 17:00）」 |
| D 日 09:00–16:59 | danger 红 + 倒數 | 「今日 17:00 前必須完成，剩餘 6h 12m」 |
| D 日 17:00 後未完成的區塊 | frozen 灰 + 鎖 icon | 「已進入強制凍結，未完成項目需 HR 解凍後才能繼續」 |
| 已全部完成 | success 绿 | 「交接已完成 ✓」 |

倒數以 **server 回傳的 `deadlineAt` + `serverNow`** 計算，不用 client clock（避免時區 / 改時間問題）。

### 3.4 C. Progress Stepper

水平四步驟，對應 PM 四件事：

1. 下屬指派
2. 模板負責人
3. 簽核代理
4. IT 權限

每步顯示：`待處理` / `進行中` / `已完成` / `卡住（原因）`。點擊 scroll 到對應區塊。若某區塊 `blocked`，stepper 該步顯示 ⚠ 並在 tooltip 顯示 `blockReason`。

### 3.5 D1. 下屬重新指派

```
┌─ 區塊一：管理的下屬 (N) ──────────────────── [全部完成 ✓] ─┐
│ 說明：請為每位下屬指定新的直屬主管                           │
│ ┌──────────────────────────────────────────────────────┐  │
│ │ 下屬姓名 │ 目前匯報線 │ 新主管 [SearchableSelect ▼] │  │
│ │ 王小明   │ 離職者本人  │ [請選擇...]                  │  │
│ └──────────────────────────────────────────────────────┘  │
│ [批次指派：選同一新主管套用到全部]                            │
└───────────────────────────────────────────────────────────┘
```

- **SearchableSelect**：搜尋同 tenant 在職員工，排除離職者本人與已離職者。
- **空狀態**：「此員工沒有直接下屬」→ 區塊自動標記完成，顯示灰底 info box。
- **驗證**：新主管不可為下屬本人（循環匯報）；不可選已離職員工（後端 validate，前端即時提示）。

### 3.6 D2. 表單模板負責人重新指派

```
┌─ 區塊二：負責的表單模板 (N) ──────────────── [2/5 完成] ─┐
│ 說明：以下模板目前由此員工負責維護，請重新指定負責人          │
│ ┌──────────────────────────────────────────────────────┐  │
│ │ 模板名稱 │ 狀態 │ 進行中簽核單 │ 新負責人 [Select ▼]  │  │
│ │ 請假單   │ 已發布│ 12          │ [已指派: 李大同]     │  │
│ │ 離職交接清單 │ 已發布│ 0       │ ⚠ 需特殊處理         │  │
│ └──────────────────────────────────────────────────────┘  │
└───────────────────────────────────────────────────────────┘
```

- 复用 FormAdmin `FormCard` 的 status badge 樣式，保持視覺一致。
- **離職交接清單模板本身**：顯示 warning callout「此模板為系統離職流程用，將自動轉移給 HR Admin 群組」，不可指派給一般員工（edge case EC-05）。
- 每列有「查看模板 →」deep link 到 `/admin/forms/[formId]`（新分頁）。

### 3.7 D3. 待簽核單跨權代理

```
┌─ 區塊三：待簽核單 (N) ──────────────────── [進行中] ─┐
│ 說明：以下簽核單仍待此員工簽核，請指定代理人              │
│ [篩選: 全部 ▼] [僅顯示逾截止風險]                        │
│ ┌──────────────────────────────────────────────────┐  │
│ │ 單號 │ 表單 │ 申請人 │ 停留天數 │ 代理人 [Select]  │  │
│ │ #8821│ 請假 │ 陳小華 │ 3       │ [張經理]          │  │
│ └──────────────────────────────────────────────────┘  │
│ ⚠ 有 2 張簽核單預計在 D+1 才會回到此節點（仍可先指定代理）  │
└───────────────────────────────────────────────────────┘
```

- 复用 `ApprovalStatus` 元件的 status chip。
- 代理人選定後即時 PATCH；若 BACKLOG-002 race 未解，顯示「同步中…」並以 polling 確認（與現有 `useApprovalSync` 策略一致）。
- **空狀態**：「沒有待簽核項目」→ 自動完成。

### 3.8 D4. 內部系統權限清單

```
┌─ 區塊四：最近 30 天使用的內部系統 (N) ────── [待 HR 確認] ─┐
│ 說明：請 HR 確認後通知 IT 收回權限（MVP：手動確認）            │
│ ┌──────────────────────────────────────────────────────┐  │
│ │ ☑ │ 系統名稱 │ 最後使用 │ 權限等級 │ 備註              │  │
│ │ ☑ │ Jira    │ 2026-05-20│ Admin   │                   │  │
│ │ ☑ │ Confluence│ 2026-05-18│ Read  │                   │  │
│ └──────────────────────────────────────────────────────┘  │
│ [全選] [複製 IT 通知範本] [標記已通知 IT]                     │
└───────────────────────────────────────────────────────────┘
```

- MVP：**唯讀清單 + HR 手動勾選確認**，不做 IT API 自動化。
- P1：「一鍵建立 IT ticket」按鈕（若後端整合 ServiceNow / Jira SM）。
- **空狀態**：「過去 30 天無內部系統使用紀錄」→ 顯示 info + 「仍建議 HR 人工確認 SSO 權限」。

### 3.9 E. Footer Actions

| 按鈕 | 可見條件 | 行為 |
|------|----------|------|
| 完成交接 | 四區塊皆 complete + 狀態 in_progress | POST complete，需 confirm modal |
| 申請延長截止 | HR + 狀態非 complete/frozen | 開 modal 填原因与新 deadline |
| 匯出 PDF/CSV | 永遠 | 下載交接紀錄 |
| 解凍（HR only） | frozen | POST unfreeze，需填原因 |

## 4. 互動與 UX 原則

1. **樂觀更新最小化**：離職交接涉及合規，mutation 成功後才更新 UI；loading / error toast 明確。
2. **區塊可獨立完成**：不必按順序，但 stepper 視覺上引導 1→4。
3. **卡住狀態可見**：任何區塊缺必要資料（如無可選主管）時，區塊 header 顯示 `blocked` + 原因，全局狀態同步為 `blocked`。
4. **多 tenant 隔離**：切換 tenant 時清空 checklist cache（呼應 team-chat #4801 跨公司資料問題）。
5. **RSC + Client 混合**：詳情頁 shell 用 RSC 拉初始資料；四區塊內 interactive table 用 client component + Jotai atom scoped by `checklistId`（沿用 FormAdmin 模式）。

---

## 5. 響應式與無障礙

- 倒數 banner 同時有 `aria-live="polite"` 供螢幕閱讀器。
- 凍結態 focus trap 在 read-only 提示 modal（首次進入 frozen 頁時）。
- 表格在小螢幕改 accordion 逐區塊展開。
